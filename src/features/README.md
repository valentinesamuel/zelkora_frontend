# `src/features/` — the feature-module contract

A **feature** is a vertical slice that *understands a domain*. If a piece of code knows what
"auth", "profile", "billing", or "lab result" means, it belongs in a feature — not in
`src/components/`.

Features that exist today: **`auth/`** and **`profile/`**. That is the complete list. Do not
pre-create directories for domains that do not exist yet.

---

## Allowed subdirectories

Inside `src/features/<feature>/`, only these subdirectories are sanctioned:

| Subdir        | Holds                                                                 |
|---------------|-----------------------------------------------------------------------|
| `components/` | Domain-aware React components used only by this feature.              |
| `api/`        | HTTP + TanStack Query hooks for this domain (see D-4 below).           |
| `hooks/`      | Domain-aware React hooks.                                             |
| `schemas/`    | Zod schemas (validation, parsing).                                    |
| `types/`      | TypeScript types/interfaces for the domain.                           |
| `pages/`      | Route-level components rendered by the router.                        |

Small features may keep a flat file instead of a directory (e.g. `auth/schemas.ts` rather than
`auth/schemas/`). Promote a file to a directory when it genuinely needs to split — not
speculatively. Do not invent a seventh category; if something does not fit any of the six, that
is a signal it is either a generic component (→ `src/components/`), a cross-cutting utility
(→ `src/lib/`), or a new feature.

## Naming conventions

| Kind                  | Convention                | Example                          |
|-----------------------|---------------------------|----------------------------------|
| Zod schema module     | `something.schema.ts`     | `login.schema.ts`                |
| Type module           | `something.types.ts`      | `session.types.ts`               |
| API / query module    | `something.api.ts`        | `profile.api.ts`                 |
| Hook                  | `useSomething.ts`         | `useCurrentUser.ts`              |
| Component             | `PascalCase.tsx`          | `CredentialsStep.tsx`            |
| Page                  | `PascalCase.tsx`          | `LoginPage.tsx`                  |

shadcn's own lowercase file convention in `src/components/ui/` (`button.tsx`, `card.tsx`) is
deliberate and preserved — it does not apply inside `features/`.

## Banned module names

These names are **banned** as file or directory names anywhere under `src/features/`:

```
utils   helpers   misc   common   data   stuff   manager   handler
```

They describe nothing, so they attract everything and become unreviewable dumping grounds. Name
a module after *what it does* or *what domain concept it owns* (`deviceLabel.ts`, `tokenStore.ts`,
`session.types.ts`).

**One sanctioned exception:** `src/lib/utils.ts`. It is generated by shadcn, holds only `cn()`,
and is referenced by `components.json` (`"utils": "@/lib/utils"`). **Do not rename or move it** —
doing so breaks every future `npx shadcn add`. The exception does not generalise: it does not
license a `utils.ts` inside a feature.

## A feature never imports another feature's internals

```
features/profile/**  ✗ import ... from '@/features/auth/tokenStore'
```

Cross-feature reuse is a design signal, not a shortcut. Resolve it one of three ways:

1. Lift the generic part into `src/components/` (see the promotion rule in
   `src/components/shared/README.md`) or `src/lib/`.
2. Move the shared concept into whichever feature genuinely owns it, and have the other feature
   depend on an explicitly-exported, documented surface — not an internal file.
3. Recognise it as a third domain and give it its own feature.

Dependency direction across the app is **`features → shared → form/ui`**. Lower layers never
import upward: `src/components/**` importing `**/features/**` is an ESLint error (INV-L2,
`no-restricted-imports` in `eslint.config.js`).

## D-4 — domain query hooks live in the feature, not a global `src/api/`

TanStack Query is wired as **infrastructure only** (`src/app/providers/`: a singleton
`QueryClient` plus dev-only devtools). Domain query hooks belong at:

```
src/features/<domain>/api/<something>.api.ts
```

There is **no global `src/api/` directory**, and one should not be created. This is a deliberate,
recorded divergence from `.claude/knowledge/stack.md`, which documents a global `src/api/` seam —
see `D-shadcn-tailwind-4` and `D-shadcn-tailwind-6(c)` in
`.claude/.artifacts/design/decisions.md`. It is not an oversight.

Two rules survive that divergence:

- **INV-14** — all HTTP goes through the single seam `apiRequest` in `src/lib/apiClient.ts`. No
  component, hook, store, or query function calls `fetch` directly.
- **D-4** — the auth session lifecycle (bootstrap / refresh / login) is **client state** and stays
  on Zustand + `apiClient`. Do not convert it to `useQuery`.

## No barrel files

There are no `index.ts` barrels in `src/`, deliberately. Use explicit path imports
(`@/features/auth/authStore`). Barrels hide the dependency graph, defeat the INV-L2 lint rule's
path-pattern matching, and hurt tree-shaking.
